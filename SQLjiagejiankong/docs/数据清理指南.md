# 价格监控系统 - 数据清理指南

## 概述

数据清理工具用于删除历史价格快照，减少数据库体积。系统**保留最近 3 个自然日**的数据（今天、昨天、前天），自动清理更早的批次。

**重要提示**：
- 清理只删除**批次**和**价格快照**
- **商品、SKU、价格阈值永久保留**（永远不会被删除）
- 清理前必须先归档，确保数据可恢复

---

## 保留规则示意

假设今天是 **2026-11-03**：

```
截止时间 = 前天 00:00:00 = 2026-11-01 00:00:00（北京时间）

时间线：
  10-19 ─── 10-24 ─── 10-25 ─┬─ 11-01 ─── 11-02 ─── 11-03
                              │
                          截止时间
  ←─────── 清理候选 ───────→  ←──── 保留 ────→
```

**保留**：11-01、11-02、11-03 的批次  
**清理**：10-31 及之前的所有批次

## 使用步骤（三步法）

### 第一步：预览（只读，安全）

查看哪些数据将被清理，**不会修改数据库**。

```bash
npm run cleanup:preview
```

**输出示例**：
```
候选批次总数: 5
候选价格快照总数: 287

候选批次列表:
  批次 8: 2026-10-19 08:49:06 | 快照=15条
  批次 9: 2026-10-24 03:05:13 | 快照=68条
  ...

保留批次总数: 2
保留批次列表:
  批次 13: 2026-11-01 17:56:42 | 68条
  批次 14: 2026-11-02 13:14:29 | 68条

已生成清理计划: data/cleanup-plans/cleanup_2026-11-03_xxxxx.json
```

**核对要点**：
- ✅ 保留的批次是否包含最近 3 天
- ✅ 候选批次的时间是否都早于"截止时间"
- ✅ 候选快照数量是否合理

---

### 第二步：归档（导出备份）

将候选数据导出为 JSON，**必须在执行删除前完成**。

```bash
npm run cleanup:archive -- --plan data/cleanup-plans/cleanup_2026-11-03_xxxxx.json
```

**参数说明**：
- `--plan`：第一步生成的计划文件路径（复制粘贴）

**输出示例**：
```
--- 归档统计 ---
商品数: 1
SKU 数: 83
批次数: 5
快照数: 287

归档文件: data/archive/cleanup_2026-11-03_xxxxx_2026-11-03.json
文件大小: 53.10 KB
```

**核对要点**：
- ✅ 批次数、快照数与预览一致
- ✅ 归档文件已生成（记录文件路径）

---

### 第三步：执行删除（不可逆）

**⚠️ 警告**：此操作会**永久删除**数据库中的批次和快照，无法撤销！

```bash
npm run cleanup:execute -- \
  --plan data/cleanup-plans/cleanup_2026-11-03_xxxxx.json \
  --archive data/archive/cleanup_2026-11-03_xxxxx_2026-11-03.json \
  --confirm cleanup_2026-11-03_xxxxx
```

**参数说明**：
- `--plan`：计划文件路径
- `--archive`：归档文件路径（第二步生成的）
- `--confirm`：计划 ID（从预览输出复制，用于二次确认）

**输出示例**：
```
--- 校验归档完整性 ---
归档批次校验: 通过
归档快照校验: 通过

--- 校验候选数据一致性 ---
候选批次: 一致
候选快照数: 一致

--- 执行删除 ---
将删除: 批次数: 5, 快照数: 287
删除成功

剩余批次数: 2
```

**安全机制**：
- 归档损坏 → 拒绝执行
- 数据库已变化（有新采集） → 拒绝执行
- 使用事务保护，失败自动回滚

---

### 第四步：重启服务器（必须）

清理完成后，**必须重启 Web 服务器**才能在前端看到更新。

```bash
# Linux/Mac
fuser -k 3000/tcp
node server.js &

# 或者手动停止旧进程后重启
# Ctrl+C 停止，然后 node server.js &
```

**验证**：刷新浏览器，批次下拉列表应只显示保留的批次。

## 数据恢复（仅测试用）

**仅用于恢复演练或开发测试**，不推荐用于正式库恢复。

```bash
npm run cleanup:restore -- \
  --archive data/archive/cleanup_2026-11-03_xxxxx.json \
  --db data/test_restore.db
```

**参数说明**：
- `--archive`：归档文件路径
- `--db`：目标数据库（**强烈建议用新文件名，避免覆盖正式库**）

**注意**：
- 恢复到**已有数据库**会追加数据（批次 ID 自增）
- 恢复到**新数据库**会创建表结构（简化版，缺少正式库的某些字段）

## 常见场景

### 场景 1：定期清理（每周一次）

```bash
# 1. 预览
npm run cleanup:preview

# 2. 核对输出，确认无误后归档
npm run cleanup:archive -- --plan <计划路径>

# 3. 执行删除
npm run cleanup:execute -- --plan <计划> --archive <归档> --confirm <ID>

# 4. 重启服务器
fuser -k 3000/tcp && node server.js &
```

---

### 场景 2：误删恢复（使用归档）

**前提**：执行删除前已完成归档。

```bash
# 1. 停止服务器
fuser -k 3000/tcp

# 2. 恢复数据到正式库
npm run cleanup:restore -- \
  --archive data/archive/cleanup_xxx.json \
  --db data/price_monitor_new.db

# 3. 重启服务器
node server.js &
```

**警告**：
- 批次 ID 会变化（例如原 1-5 恢复后变为 8-12）
- SKU ID 保持不变（因为 SKU 从未被删除）

---

### 场景 3：查看历史数据（不恢复到正式库）

```bash
# 恢复到临时数据库查看
npm run cleanup:restore -- \
  --archive data/archive/cleanup_xxx.json \
  --db data/temp_view.db

# 用 SQLite 工具打开 temp_view.db 查询
sqlite3 data/temp_view.db "SELECT * FROM collection_batches;"
```

## 故障排查

### 问题 1：归档失败 "批次不存在"

**原因**：计划生成后，数据库发生变化（新采集或手动删除）。

**解决**：重新执行预览，生成新的计划文件。

---

### 问题 2：执行失败 "候选数据已变化"

**原因**：归档后、执行前，数据库发生变化。

**解决**：
1. 检查是否有采集任务正在运行 → 停止采集
2. 重新执行预览 → 归档 → 执行

---

### 问题 3：前端显示批次数量不变

**原因**：服务器内存缓存了旧数据。

**解决**：重启服务器（见"第四步"）。

---

### 问题 4：归档文件损坏

**检查方法**：
```bash
# 查看归档内容
cat data/archive/cleanup_xxx.json | head -50
```

**特征**：
- 文件大小异常（< 1 KB 或被截断）
- JSON 格式错误

**解决**：重新归档。归档失败时会生成临时文件（`.tmp` 后缀），正式文件不会发布。

## 文件说明

| 目录/文件 | 说明 |
|-----------|------|
| `data/cleanup-plans/` | 清理计划（JSON），包含候选批次 ID、时间、快照数 |
| `data/archive/` | 归档文件（JSON），包含完整的商品、SKU、批次、快照数据 |
| `data/cleanup-logs/` | 执行日志（JSON），记录删除操作的时间、结果 |

**保留期限建议**：
- 计划文件：执行后可删除（1 周）
- 归档文件：**至少保留 1 个月**（用于误删恢复）
- 执行日志：保留 3 个月（审计用）

## 技术细节（进阶）

### 时区处理

- 所有时间计算基于 **Asia/Shanghai** 时区
- 截止时间 = 前天 00:00:00（北京时间）
- 数据库存储时间为字符串格式（YYYY-MM-DD HH:MM:SS）

### 数据完整性校验

归档和执行都使用 **SHA-256 校验和**：
- 批次数据校验：`JSON.stringify(batches)` 的哈希
- 快照数据校验：`JSON.stringify(snapshots)` 的哈希

任何校验失败都会**拒绝执行**并回滚。

### 事务保护

执行删除使用 **BEGIN EXCLUSIVE TRANSACTION**：
1. 先删除快照（外键依赖）
2. 再删除批次
3. 任一步骤失败 → 全部回滚

### 跳过的批次状态

- `importing`：正在采集中，跳过清理
- 其他状态（`success`、`failed`、`partial`）：按时间规则清理

## 安全建议

1. **首次使用前测试**  
   在测试数据库上完整走一遍流程，熟悉命令。

2. **定期归档**  
   即使不执行删除，也定期归档历史数据。

3. **异地备份**  
   重要归档文件定期复制到其他机器或云存储。

4. **清理前检查**  
   - 确认没有采集任务运行
   - 确认保留的批次符合业务需求
   - 核对归档文件大小（正常应 > 10 KB）

5. **服务器重启**  
   删除后立即重启，避免前端显示脏数据。
